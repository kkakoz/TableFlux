## Context

TableFlux 前端为 React + Vite + Tailwind CSS 4，业务 UI 集中在 `frontend/src`（含大型 `App.tsx` 与多份组件级 `*.css`）。当前样式在页面与面板间存在间距、按钮高度不一致等问题，与「桌面数据库客户端」常见的信息密度期望有差距。本变更仅触及呈现层与开发约定，不改变 Wails API 或数据流。

## Goals / Non-Goals

**Goals:**

- 用少量可复用的尺寸与间距约定（设计令牌或 CSS 变量 + 语义化类名）统一紧凑型布局。
- 将主要按钮、图标按钮、工具栏控件收敛到明确的小尺寸规范，减少各文件中的重复魔法数。
- 在 Cursor 规则中记录上述约定，使新代码默认遵循同一套紧凑样式。

**Non-Goals:**

- 不 redesign 品牌色、不更换图标库或表格/编辑器第三方组件的默认主题（除非为对齐紧凑尺寸所必需的最小覆盖）。
- 不修改 Go 后端、Wails 绑定或数据库访问逻辑。
- 不要求一次性重写所有历史内联样式；允许分阶段替换，但新增与修改的代码须符合新约定。

## Decisions

1. **令牌载体：CSS 变量 + 可选 Tailwind 主题扩展**  
   - **理由**：与现有 `*.css` 并存友好，表格/Monaco 等也可读取变量；Tailwind 若已有 `@theme` 可映射到同一变量避免双源。  
   - **备选**：仅用 Tailwind 任意值 — 对非 Tailwind 的纯 CSS 文件不够统一。

2. **「小按钮」以最小触摸/点击目标为下限**  
   - **理由**：桌面端仍以鼠标为主，但需避免低于约 24–28px 的可点击高度导致误触与可访问性问题；具体数值在实现时落在紧凑区间（如 `py-1`/`h-7` 量级），在 spec 中表述为「统一且小于当前默认大块按钮」。

3. **Cursor 规则内容**  
   - **理由**：规则文件只写「必须遵守的命名、文件位置、何时用变量/类名、禁止事项」，不写具体像素表（像素表以代码与 spec 为准，避免规则与实现漂移）。  
   - **备选**：把完整令牌表只放在规则里 — 易与代码不同步。

4. **迁移策略**  
   - 先全局/根级与高频组件（顶栏、侧栏、设置、对话框按钮）对齐，再按需扫次要面板；避免单次超大 diff。

## Risks / Trade-offs

- **[风险] 紧凑化导致部分文案截断或控件拥挤** → 在主要流程（连接、查询、设置）做视觉抽查；必要时仅对长文案区域保留略大行高而非放大整按钮。  
- **[风险] Tailwind 与裸 CSS 混用导致优先级战争** → 优先用变量与低特异性选择器；避免在多处用 `!important`。  
- **[权衡] 分阶段收敛** → 短期内新旧样式可能并存，通过「新改必跟约定」控制风险。

## Migration Plan

1. 引入/对齐设计令牌与根级紧凑变量（若已有则合并）。  
2. 替换全局按钮与表单控件基类或组件封装。  
3. 按模块收敛 `components/*.css` 与 `App.tsx` 内重复尺寸。  
4. 添加 Cursor 规则并做一次全前端构建验证。

## Open Questions
